# Задержка превью ленты: до и после

Проверено 26 октября 2026 года в development preview через общий HTTP-прокси
`localhost:80`, без публикации в production. Это измерение API, не Lighthouse
и не скорость загрузки страницы на мобильной сети.

## Причина и изменение

Даже готовая курируемая миниатюра проходила `exists()` в подготовке варианта,
повторное разрешение исходника и `getMetadata()` перед HEAD, 304 или чтением тела.
Готовность файла в App Storage не устраняла эти сетевые проверки.

Для девяти **заранее одобренных публичных примеров** подготовлены девять WebP и
три коротких MP4. Отдельные производные хранятся в App Storage под именами с
SHA-256; оригиналы не изменены. Фиксированный манифест содержит имя объекта,
поколение, размер и SHA-256. Запросы курируемых превью не запускают генерацию,
проверку существования, чтение метаданных или запрос публикации.

- HEAD, 304 и отклонение некорректного range работают только по манифесту.
- Первый GET читает только закреплённое поколение объекта, ограничивает чтение
  размером + 1 байт и проверяет размер и SHA-256 перед отдачей.
- Успешно проверенные публичные байты сохраняются в памяти процесса, с
  объединением одновременных чтений. Все 12 файлов занимают **336 626 байт**.
  Пользовательские файлы и решения о доступе туда не попадают.
- Клиент добавляет `?v=<sha256>` только для известных вариантов примеров.
  Только точная версия получает `public, max-age=31536000, immutable`.
  Старые URL без версии работают с `public, no-cache`; неверная версия — 404
  `no-store`, без возврата другой версии под старым URL.
- Неизвестные ID, URL вместо ID, неподдерживаемые варианты и прототипные имена
  не разрешаются в путь хранилища. Нового прокси произвольных URL нет.
- Ошибка чтения/контрольной суммы не кешируется как успешное медиа: ответ 503
  `no-store`, без заголовков размера/range/ETag производного файла.

Пользовательские публикации остаются на прежнем отдельном пути:
актуальная проверка `published` перед подготовкой и после неё, сравнение
текущего исходника, затем условный ответ/range. Ответы — `private, no-cache`;
недоступные работы — 404 `no-store`. Параметр `v` не меняет эту политику.
Доступ и снятие с публикации не кешируются.

## Методика измерения

До изменения API запущен из исходной версии. После изменения API перезапущен,
кеш курируемых байтов пуст. Для каждого варианта последовательно выполнены:
первый HEAD, повторный HEAD, первый GET тела, повторный GET тела, GET с
совпадающим `If-None-Match`. HEAD не прогревает кеш тела. Во всех GET после
изменения проверена SHA-256 полученных байтов. HTTP-клиент без собственного кеша.
Производные до изменения уже существовали: время их первой генерации в сравнение
не включено. «Первый» означает первый запрос этого варианта в последовательности,
а не новый сервер/новое TLS-соединение для каждого файла.

Перезапуск процесса очищает небольшой кеш байтов. Предварительной массовой
загрузки видео в браузер нет.

## Проверки

`pnpm --filter @workspace/api-server test --feed-media` — 8 проверок прошли:

- отказ после снятия публикации до 304, HEAD и диапазона байтов, в том числе с
  условными заголовками и параметром версии;
- снятие публикации во время подготовки производного файла;
- HEAD/304 всех 12 курируемых вариантов без метаданных, проверки существования,
  энкодера или запроса публикации;
- обычный range, suffix, open-ended, неверный/многосоставной/небезопасный range,
  правильный и устаревший `If-Range`;
- изоляция публичного кеша, объединение чтений, контрольная сумма и повтор после
  ошибки; отсутствие оригинала как fallback при отказе превью;
- реальное кодирование WebP ≤480 px и немого MP4 ≤6 секунд без изменения исходника.

Все 12 настоящих вариантов вернули 200 и затем 304. Дополнительно для всех
трёх настоящих MP4 проверены 206 с `bytes=0-1023`, `bytes=-123`, `bytes=1024-`:
число байтов и `Content-Range` совпадают. ffprobe подтвердил один видеопоток:
Genjutsu 270×480 / 6 с, Sintel 480×204 / 6 с, flower 480×270 / 5 с.
WebP — 3 178–42 122 байта. Настройки 480 px, 12 fps, отсутствие аудио,
ограничения autoplay, `loading="lazy"` и `preload="none"` сохранены.

Проверки типов API и frontend прошли. Оба workflow запускаются.
Мобильная главная 402×874 отображается без ошибок браузера.
Состояния ленты, требующие взаимодействия, подтверждены кодом и HTTP-тестами,
не выдаются за полноценный браузерный сценарий.

## Обновление примеров

После намеренного изменения одобренных исходников или энкодера выполнить:
при изменении настроек энкодера сначала повысить `FEED_VERSION`, чтобы не
переиспользовать старые производные.

```sh
pnpm --filter @workspace/scripts run prepare:curated-feed
```

Скрипт берёт только фиксированный список публичных примеров, готовит производные
существующим ограниченным энкодером, проверяет формат/геометрию/длительность,
создаёт новые content-addressed объекты без перезаписи, сверяет сохранённые байты
и только затем обновляет `lib/studio-examples/feed-media.json`.
Манифест и frontend/API должны выпускаться согласованно. Отсутствующий объект
не запускает генерацию или выдачу оригинала в запросе посетителя.

Маскоты, `home-*`, оригиналы, Canvas, владелец и финансы не изменены.
